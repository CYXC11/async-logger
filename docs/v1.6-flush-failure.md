# V1.6 异步 `flush()` 故障复盘

`AsyncLogger::flush()` 把 `FlushRequest` 放入日志队列，解锁后等待自己的 `future`。后台线程按 FIFO 处理任务，确认文件流已刷新才报告成功。发生故障时，后台线程应先停止接收新任务，再把错误交给正在等待的调用者。队列里尚未处理的刷新请求也要收到结果。[异步实现](../src/async_logger.cpp)

## 先发布失败状态，再完成请求

在对话「审查 V1.6 异步 flush」中，用 `/dev/full` 触发文件流刷新失败后暂停后台线程。调用者收到 `File flush failed` 后紧接着调用 `log()`，这条日志仍然成功入队。

| 顺序 | 后台线程 | 调用线程 |
| --- | --- | --- |
| 1 | 文件流刷新失败，内层 `catch` 调用 `set_exception()`。 | `future` 就绪，`get()` 抛出异常。 |
| 2 | 还没进入外层 `catch`，`worker_failed_` 和 `stopping_` 都是 `false`。 | 捕获异常后调用 `log()`。取得 `mutex_` 后检查状态，随后入队。 |
| 3 | 外层 `catch` 设置失败状态并清空队列。 | 刚入队的日志被丢弃。 |

两个标志的读写都有锁保护。`set_exception()` 使共享状态就绪后，调用者就可以继续运行，此时 worker 还可能没拿到锁更新状态。[C++ 工作草案 `[futures.state]`](https://eel.is/c++draft/futures.state#6)

修复后，内层 `catch` 先持有 `mutex_` 设置 `worker_failed_` 和 `stopping_`，解锁后才完成当前请求。后台线程随后用 `throw;` 进入外层 `catch`，把错误交给剩余的刷新请求，丢弃未写入的日志，再唤醒等待空位的线程。`log()` 和 `flush()` 用同一把锁检查状态，收到刷新失败后再提交的请求会被拒绝。[异步实现](../src/async_logger.cpp)

`async_flush_failure_rejects_log` 在当前请求完成后暂停 worker，让外层清理暂时无法更新状态。调用线程先检查 `flush()` 抛出的 `File flush failed`，再检查 `log()` 是否抛出 `AsyncLogger worker failed`。两次检查结束后，测试才放行 worker。[故障回归测试](../tests/async_flush_failure_test.cpp)

## TSan 告警与异常对象的生命周期

同项目的「修复 FlushRequest 异常竞争」对话分析了 `async_flush_failure_releases_waiters` 的告警。worker 取出第一个刷新请求后，测试用 `std::latch` 等另外两个请求入队，再让 worker 刷新 `/dev/full`。测试要求三个调用都抛出 `std::runtime_error`，且 `what()` 都返回 `File flush failed`。[并发回归测试](../tests/async_flush_failure_test.cpp)

原始报告来自 GNU 15.2.0 的构建。两条 TSan 告警都出现在另外两个刷新请求的调用线程之间。

| 访问位置 | T3 的读取 | T4 的释放 |
| --- | --- | --- |
| `runtime_error` 的消息缓冲区 | 第 26 行比较 `what()` 的结果，底层调用 `memcmp`。 | `std::runtime_error::~runtime_error()` 调用 `operator delete`。 |
| 异常对象 | 第 26 行读取虚表指针以调用 `what()`。 | 第 27 行退出 `catch`，编译器生成的 `__cxa_end_catch` 进入异常清理，最终调用 `free`。 |

旧实现给每个请求各建一对 promise 和 future，再把同一个 `std::exception_ptr` 复制给多个 promise。复制 `exception_ptr` 后，多个指针仍指向同一个异常对象。再次调用 `std::current_exception()` 也可能得到指向该对象的指针。[C++ 工作草案 `[propagation]`](https://eel.is/c++draft/propagation)

当时的 libstdc++ 每次执行 `std::rethrow_exception()` 都会新建一份展开记录，指向原始异常，并给它的原子引用计数加一。退出 `catch` 时，运行库清理对应记录并释放引用。最后一个引用释放时，运行库才析构原始异常。

排查时用报告里的 `libstdc++.so.6` Build ID `3a7a8c6bd922e6314edb7a710fdc0293265c2c42` 核对了本机库，并检查了反汇编。TSan 能拦截消息比较和内存释放。库内的引用计数操作没有插桩，两条告警符合 TSan 漏掉这段同步时的表现。仅凭堆栈无法确认异常对象是否提前释放。[GCC 15.2 `eh_ptr.cc`](https://github.com/gcc-mirror/gcc/blob/releases/gcc-15.2.0/libstdc%2B%2B-v3/libsupc%2B%2B/eh_ptr.cc#L132-L198)

V1.6 用 `std::promise<const char*>` 传递结果。`nullptr` 表示刷新成功。写入或刷新失败时，worker 传回指向静态字符串的指针，由各个 `flush()` 调用线程自行构造并抛出 `std::runtime_error`。这样每个调用者都有自己的异常对象和消息缓冲区。未知异常继续用 `set_exception(std::current_exception())` 传播，保留原有异常信息。[失败结果交付](../src/async_logger.cpp)

## 验证记录

修复后，4 项 TSan CTest 全部通过，每项再跑 25 次也都通过。整理本文时用 GNU 15.2.0 在独立目录重新构建，完整 TSan CTest 再次通过 4/4。两条故障测试仍在受控的文件流故障下检查异常类型和错误消息。

```sh
cmake -S . -B build-tsan -DCMAKE_BUILD_TYPE=Debug \
  -DCMAKE_CXX_FLAGS='-fsanitize=thread -g -fno-omit-frame-pointer'
cmake --build build-tsan --parallel
ctest --test-dir build-tsan --output-on-failure
ctest --test-dir build-tsan --output-on-failure --repeat until-fail:25
```
